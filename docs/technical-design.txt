1. Introduction
1.1 Purpose
This Technical Design Document (TDD) describes how the Platform specified in the Software Requirements Specification (SRS) will be built. The SRS states what the system must do and how well; this document states how: the architecture, technology choices, module boundaries, data model, the algorithms for the hard problems (idempotent order processing, uncertain payments, offline synchronisation, dispatch), the deployment model and the cost strategy. Requirements are cited by SRS identifier and are not restated. Rejected alternatives are recorded where cost, connectivity or regulation drove the decision.
1.2 Scope
The design covers the complete Platform defined in the SRS: the customer web (Next.js) and mobile (React Native) apps, the merchant dashboard, the delivery agent native app (React Native, Android 8.0+ primary, iOS 15+ secondary), the administrative dashboard, and an Express (Node.js, TypeScript) modular-monolith backend with PostgreSQL, an event queue, a payment adapter layer, notifications and geospatial matching, together with security, regulatory compliance, observability, deployment and testing.
1.3 Relationship to the SRS
SRS identifiers (FR-CUS, FR-MER, FR-DEL, FR-ADM, FR-SYS, PR, NFR, BR, CT, DC, NN) are reused so that every design decision traces to a requirement; the requirements themselves are not repeated here. Where a short label used in this document differs from the identifier in the final SRS (the NFR-nn and PR-nn labels and a few FR-SYS-nn and DC-nn labels), Appendix C gives the crosswalk.
The SRS leaves some decisions open (its Appendix F). This document proposes a default for each one that affects the design and marks it so the team can confirm or overrule it (Chapter 18).
1.4 Conventions
Numbers marked as budgets or assumptions are design inputs to be validated during the pilot, not measurements.
Prices and free-tier limits were researched in November 2026 and change often; each is dated and listed with its source in Appendix B. Confirm them on the provider’s page before committing.
2. Architecture Principles
One language, six repositories. TypeScript everywhere, with each of the six deliverables (API, customer web, merchant web, admin web, customer mobile, rider mobile) in its own repository. The API’s OpenAPI document, documented with Swagger UI, is the single source of truth for every repository; it, not shared source code, keeps the backend and the clients in agreement.
Every write is a command with an idempotency key. Retrying a command can never create a second effect.
State changes are events. Every order or payment transition writes an event to an outbox table in the same database transaction; consumers react asynchronously.
Interfaces at every paid or external boundary. Payments, SMS, push, maps, storage, queue and geo-index are behind ports so that the free implementation used at the pilot can be replaced without touching business logic.
3. Technology Stack and Cost Strategy
3.1 Selection Criteria
Each technology was accepted only if it met all of the following: (1) compatible with the mandated React Native, Next.js and Express stack; (2) a free tier that is usable for the pilot and that permits commercial use; (3) no card-on-file requirement where avoidable; (4) a documented exit path to a paid plan or to an equivalent open-source alternative; (5) acceptable latency from Cameroon, meaning a European or global edge location rather than a single US-only region.

4. System Architecture
4.1 Architectural Style
The backend is a modular monolith in its own repository (resto-api). Inside each module the code is layered as routes, controllers, services and repositories: routes declare endpoints and middleware, controllers handle HTTP, services hold the business rules, and repositories are the only code that talks to PostgreSQL. Services never touch Express or SQL directly. Calls to paid or external providers (payments, SMS, push, storage, queue, geo-index) go through small interfaces (ports) that adapters implement. This gives three benefits that matter here: free-tier components can be replaced without rewriting business logic, services can be tested with fake repositories and adapters, and a module can later be extracted into a service by replacing its in-process calls with network calls.
Modules communicate in two ways only: synchronous calls through a module’s public interface, and asynchronous domain events through the outbox (Chapter 6). A module may never read another module’s tables directly. This rule is enforced in code by lint rules (dependency-cruiser) and in the database by separate schemas per module.

 | 4.6 Backend Code Structure
Each module follows the same four-layer folder structure: routes, controllers, services and repositories. A request flows downward through the layers and a response flows back up; a layer may only call the layer directly beneath it.
Routes. Declare the URL, HTTP method, middleware (authentication, role check, rate limit, idempotency guard) and the zod schema for each endpoint. No logic.
Controllers. Read the validated request, call exactly one service method, and map the result or error to the standard response envelope. No business rules and no SQL.
Services. Hold the business rules: invariants, the order and payment state machines, fee and money calculations. A service opens the database transaction, calls repositories, writes outbox events, and calls ports for external providers. Services call other modules only through that module’s service.
Repositories. The only code that runs SQL. Each repository belongs to one module and its tables, takes the transaction handle from the service, and returns plain typed records. A repository never calls another repository of a different module.

Single source of truth: the OpenAPI 3.1 document of resto-api is the one contract for all six repositories. It is generated from the zod schemas and route definitions in the API code, so it cannot drift from what the server actually accepts, and it is served as interactive Swagger UI documentation at /docs (and as raw JSON at /openapi.json) in development and staging; in production the page is disabled or restricted to administrators. Every release publishes a versioned copy of the document. Each client repository regenerates its API types from that copy (for example with openapi-typescript) and fails its own CI build if an API change breaks it; the mobile and web teams read the same Swagger UI page to see endpoints, schemas, error envelopes and the Idempotency-Key requirement. Breaking changes are caught by an OpenAPI diff in CI and follow the versioning rule in Chapter 12.1, so an older app version keeps working. Small helpers such as the geo and i18n utilities are deliberately duplicated per repository rather than shared, which avoids publishing and versioning a shared package.
4.8 Request Pipeline
Every HTTP request passes one ordered chain: request identifier and logging context; security headers, CORS allow-list and body size limit; rate limiting; authentication; authorisation (role and ownership); input validation with the route’s zod schema (unknown fields rejected); idempotency guard for mutating routes (Chapter 6); controller, which calls the service inside a database transaction (the service calls the repositories); error mapper to the standard error envelope without leaking internals (NFR-39).

 | 5. Domain Model and Class Design
5.1 Conventions
Identifiers are UUIDs (version 7, time-ordered, which keeps B-tree indexes compact and inserts append-friendly).
Money is stored as an integer number of FCFA (XAF has no minor unit), in a Money value object; floating point is never used for money.
Timestamps are stored in UTC (timestamptz) and displayed in the Africa/Douala time zone.
Entities are never hard-deleted when they have financial or audit significance; they are marked inactive or archived.
Orders and order items store snapshots of names and prices at submission time so later menu edits never change history (SRS 3.3.3).

 | 5.4 Address Asset Design
Buea addressing is landmark-relative and map pins are often 50 to 100 m off (CT-4). The address asset therefore stores more than coordinates and improves with use.
Rider pin correction (FR-DEL-4.5): on arrival the rider may move the pin. The correction is stored as a PinCorrection with the rider, the time and a confirmation count, linked to the address; the original pin is never overwritten.
Promotion rule: a corrected pin becomes the address’s effective pin after one correction by a verified rider, and is re-confirmed when a later delivery ends within 30 m of it. If two corrections disagree by more than 100 m, the address is flagged for admin review.
6. Order State Machine and Idempotency Design
The order state machine is the most important mechanism in the Platform (DC-03, FR-SYS-01). Every transition is idempotent, versioned and event-emitting; duplicate charges and phantom deliveries are treated as engineering defects. This chapter specifies the order and delivery state machines, the versioning rule, the idempotency mechanism and the outbox that turns state changes into events.
6.1 Order State Machine
The commercial lifecycle of an order (what the customer and merchant see) is separated from the logistic lifecycle of its delivery (what the rider does). The two machines are coordinated through events, which keeps each small and testable.

 | 6.2 Delivery State Machine

The rider app triggers AT_PICKUP, PICKED_UP, AT_DROPOFF, DELIVERED and FAILED as commands that may be created offline and replayed later; each carries a client action identifier and the device time at which the action happened, so the server stores both the occurrence time and the receipt time (Chapter 9).
6.3 Versioned, Optimistic Transitions
Every aggregate row carries an integer version. A transition succeeds only if the row still has the status and version the caller read; otherwise the transition is rejected as a conflict and the caller re-reads. This removes lost updates when a merchant accepts at the same moment the customer cancels, or when an admin override races a rider action.
The three writes (state, event history, outbox) share one database transaction. A transition therefore either happens completely, with its history and its event, or not at all. The unique constraint on (order id, version) in the event table is the last line of defence against a double transition.
6.4 Idempotency Design
Mobile networks drop mid-request, and the rider app replays queued actions after reconnecting. The system must never double-charge or double-order (NN-2, FR-SYS-02, NFR-22).
6.4.1 Key Rules
The client generates a UUID idempotency key when the user performs the action, stores it before sending, and reuses it on every retry of that action.
The key is sent in the Idempotency-Key header on every POST, PUT, PATCH and DELETE.
The server scopes a key by user and route, and stores a hash of the request body with it.
Same key and same body: the stored response is returned and nothing is executed again.
Same key and different body: rejected with 422 (a client bug).
Same key while the first request is still running: 409 with Retry-After; the client waits and retries.
Keys expire after 24 hours for online clients and after 30 days for keys created by the rider app, because a rider can be offline for long periods.
6.4.2 Storage
CREATE TABLE platform.idempotency_keys (
  scope           text        NOT NULL,   -- user id plus route
  key             uuid        NOT NULL,
  request_hash    bytea       NOT NULL,

PostgreSQL is the source of truth (ADR-005). The claim is an INSERT that relies on the primary key: the first request inserts IN_PROGRESS and proceeds, a concurrent duplicate hits the conflict and is told to wait. When Redis is available it caches completed responses to avoid a database read on replays, but correctness never depends on it.

6.7 Cancellation and Refund Rules (Proposed, see OD-03 and OD-04)
Automatic customer cancellation is allowed in PENDING_PAYMENT and in PLACED before the merchant accepts.

7. Payment, Wallet and COD Reconciliation Design
The strategic bet of the project is that winners solve cash-on-delivery reconciliation and payment collection reliability better than anyone else. This chapter therefore specifies the payment adapter, the payment state machine including the UNKNOWN state, the double-entry ledger that backs rider wallets and merchant balances, and the reconciliation jobs that keep money consistent.
7.1 Payment Adapter Interface
Business logic talks to one interface; each provider (an aggregator at launch, direct MTN MoMo and Orange Money later) implements it (DC-04, FR-SYS-03).
// ports/paymentPort.ts (illustrative)
export type Channel = 'cm.mtn' | 'cm.orange';

export interface CollectRequest {
  reference: string;        // our unique payment reference, also the provider idempotency reference
  amount: Money;            // integer FCFA
  channel: Channel;
  customerPhone: string;    // E.164
  description: string;
  callbackUrl: string;
}

export type ProviderStatus = 'PENDING' | 'SUCCESS' | 'FAILED' | 'CANCELLED' | 'EXPIRED' | 'NOT_FOUND';

export interface PaymentPort {
  collect(req: CollectRequest): Promise<{ providerRef: string; status: ProviderStatus }>;
  getStatus(reference: string): Promise<{ status: ProviderStatus; providerRef?: string }>;
  parseWebhook(headers: Headers, rawBody: Buffer): WebhookEvent;   // verifies the signature
  payout(req: PayoutRequest): Promise<{ providerRef: string; status: ProviderStatus }>;
  refund(providerRef: string, amount: Money): Promise<{ status: ProviderStatus }>;
  listSettlements(day: string): Promise<SettlementLine[]>;          // for daily reconciliation
}
The adapter maps every provider-specific response to the small ProviderStatus set. It must treat a timeout, a connection reset or an unparseable response as an unknown outcome, never as a failure: it throws a ProviderUnknownError that the payments module converts to the UNKNOWN state.

 | 7.2.1 Rules for UNKNOWN (FR-SYS-03, DC-05)
UNKNOWN never triggers a refund. A refund of money that may never have been collected would lose money.
UNKNOWN never triggers a new collection for the same order with a new reference, because the first one may still succeed and the customer would be charged twice.
UNKNOWN triggers reconciliation: the worker queries the provider by our reference until the provider gives a definite answer.
The customer sees a neutral message and can keep using the app; the order is not cancelled and not confirmed.
After the final retry window the payment goes to the administrator queue with the provider reference and timestamps for manual reconciliation against the provider dashboard.

7.5 Rider Top-Up and Withdrawal Flows
Top-up: the rider enters an amount in the app; the platform creates a collection through the same PaymentPort; only SUCCEEDED credits the wallet. UNKNOWN top-ups follow the same reconciliation, so a dropped network never loses a rider’s money or credits it twice.
Withdrawal (FR-DEL-7.4): the rider requests a payout to MoMo, Orange Money or bank; a biometric check on the device and a server-issued step-up token are required (NFR-10). The ledger moves the amount to a pending account, the payout is sent with a unique reference, and the pending amount is finalised or released only on a definite provider answer. A payout with an unknown outcome is reconciled, never resent. Target settlement: within 24 business hours.
7.6 Provider Integration Notes
At launch the adapter targets a payment aggregator rather than each mobile operator (ADR-009): direct operator APIs need separate merchant agreements and production approvals, while aggregators expose MTN and Orange through one API with a sandbox (success, insufficient funds, timeout, cancellation), mobile-money transfers and webhooks. Provider, keys, callback URL and sandbox or live mode are environment configuration. Aggregator fees and settlement times come from the signed agreement (DC-09). Webhook handling is in Chapter 12.6; NECAP reporting is in Chapter 14.

8.3 Matching and Offer Flow
The ranking function at the pilot is distance first, with a small penalty for riders who recently declined or timed out. Distance is straight-line (haversine) because road routing services cost money; it is good enough for a 3 km corridor and is replaced by routed distance only if it proves misleading in practice.
8.4 Atomic Acceptance
In the pool several riders can tap Accept within the same second. Exactly one must win. The decision is made by the database, not by application code:
UPDATE dispatch.offers
   SET status = 'ACCEPTED', accepted_at = now()
 WHERE id = $1 AND status = 'OFFERED' AND expires_at > now()
RETURNING order_id;

-- unique partial index guarantees one accepted offer per order
CREATE UNIQUE INDEX one_accepted_offer_per_order
  ON dispatch.offers (order_id) WHERE status = 'ACCEPTED';
The loser receives 409 and the app shows This order was taken. Acceptance from the lock screen uses the same endpoint (FR-DEL-3.4). The rider app treats a replayed acceptance with the same idempotency key as the same decision.
8.5 Geo Index
8.5.1 In-Memory Implementation (Pilot)
The in-memory index keeps the last known point of each online rider in a map keyed by rider id and answers nearest-rider queries with a linear scan and the haversine formula. For 1,000 riders this is a few thousand arithmetic operations per query, far below one millisecond of CPU, so a dedicated spatial structure is unnecessary. Entries older than 90 seconds are ignored. Nothing is written to Redis or to PostgreSQL for ordinary pings (ADR-004).
8.5.2 Redis Implementation (Scale Path)
When a second backend instance is needed, GeoIndexPort is bound to a Redis implementation (GEOADD and GEOSEARCH) and WebSocket fan-out is bridged through Redis publish and subscribe (GEO_INDEX=redis). Because the free Upstash plan limits commands, the adapter batches location updates to one command per rider every 15 to 30 seconds and is intended for a paid or self-hosted Redis.

 | 8.7 Delivering Offers to Locked Phones
The requirement is that an offer rings like a call and can be accepted from the lock screen (FR-DEL-3.1, 3.4, NFR-24). The design combines three layers so that at least one works on every device.
Foreground: a WebSocket message opens the full-screen offer with countdown and slide-to-accept.
Background or killed app (Android): a high-priority FCM data message wakes the app, which posts a notification on a dedicated high-importance channel with a looping ringtone and vibration and Accept and Decline actions. Where the operating system allows it, the notification uses a full-screen intent so the offer screen appears over the lock screen.
Fallback: a standard high-importance notification with the same actions and a sound, which works even when full-screen intents are not permitted.
Two risks apply. Recent Android versions restrict full-screen intents to calling and alarm apps unless the user grants permission, so the team must check the current Play Console policy or accept the fallback layer. Battery-saving modes on budget handsets delay background pushes, so onboarding guides riders to exempt the app from battery optimisation and the pilot measures the 99 per cent within 5 seconds target (NFR-24) on real test devices (Chapter 17).
8.8 Offer Expiry and Timers
Each offer has an expires_at timestamp stored in the database. A delayed job (pg-boss, scheduled for expires_at) marks the offer EXPIRED and starts the next round; a periodic sweep every 10 seconds repairs any job that was lost. Both are idempotent: they only act on rows still in OFFERED. Offer timers never live only in memory, so a backend restart cannot leave an order without a rider.
8.9 Reassignment, Rider Cancellation and Admin Override
A rider who cancels after assignment (before pickup) returns the delivery to SEARCHING; the reason is recorded and the rider’s score is affected.
An administrator can reassign an order from the dispute console (FR-ADM-05); the old assignment is closed, a new offer round starts and an audit entry is written in the same transaction.

9.5 Command Queue and Sync Protocol
9.5.1 Rules
A rider action first writes a command row (and its artifacts) to SQLite in one transaction, then updates the local delivery status, then returns control to the screen. The screen never waits for the network.
Commands for the same delivery are sent strictly in seq order; commands of different deliveries are independent.
Photos and signatures are uploaded first, directly to object storage through a short-lived signed URL obtained from the API; the command then references the stored object key. An interrupted upload resumes from the saved status.
Each request carries the command id as Idempotency-Key and the device occurrence time in the body; the server stores both the occurrence time and the receipt time.
Failures use exponential backoff with jitter (for example 5 s, 15 s, 1 min, 5 min, then every 15 min) while the app is in the foreground or the background task runs; the rider can force Retry at any time (FR-DEL-6.5).
A permanent server rejection (for example the order was cancelled by an administrator) marks the command CONFLICT with the server’s message; the app shows it clearly (NFR-46) and offers Contact Support.

 | 9.6.1 Offline OTP Verification
The 4-digit delivery OTP is generated by the server when the order is accepted and is shown to the customer in the customer app and by push (ADR-007). The rider app receives a salted hash of the code with the delivery so that it can give instant feedback without a network. A 4-digit code has only 10,000 possibilities, so the local hash can be brute-forced by a malicious device; therefore the local check is only a usability aid. The rider enters the code, the app records it in the COMPLETE command, and the server performs the authoritative comparison on sync. A mismatch moves the delivery to a review state and holds the payout until an administrator resolves it. The app limits local attempts to three and logs them, and fraud rules flag riders with repeated mismatches.
9.7 Adaptive Location Service
Battery tactics (CT-2): use distance filters so the radio sleeps when the rider is still; raise accuracy only during active delivery; never poll the server (the server pushes); coalesce all pending uploads into one request per wake-up; reduce map redraws to movements above 50 m (PR-10); dim and simplify the map style; avoid wake locks outside the foreground service.
9.8 Navigation and Address Handling
Turn-by-turn through deep link: the Navigate button opens an installed navigation app with the pin as destination; the Plus Code is displayed and copyable as a fallback (FR-DEL-4.4). This avoids routing fees and navigation SDK licences.
In-app map: MapLibre shows the rider, restaurant and customer pins on self-hosted tiles; the Buea corridor region is downloaded when the rider first goes online on Wi-Fi so that it works offline (FR-DEL-4.6).
9.9 On-Device Security
Access and refresh tokens are kept in secure storage; they are never written to SQLite or logs.
The local database can be encrypted when the SQLCipher option of the SQLite module is confirmed to work with the chosen SDK; otherwise personal data is minimised and purged after sync (NFR-13).
Biometric confirmation is required for withdrawals, wallet top-ups and COD above a configurable value (NFR-10).

11. Data Design
11.1 Principles
One PostgreSQL database with one schema per module (identity, catalog, cart, ordering, payments, dispatch, delivery, notifications, support, admin, analytics, platform). A module reads another module’s data only through its public interface or through events (Chapter 4.1).
Constraints in the database repeat the most important invariants of Chapter 5.3, so a bug in application code cannot corrupt financial data.
Financial and audit tables are append-only. State tables carry a version column.

11.3 Key Constraints
The constraints that carry the design are listed in Chapter 5.3; the ledger is append-only and balanced by a deferred constraint trigger and revoked UPDATE and DELETE privileges (Chapter 7.4). Full migrations live in the migrations folder of the resto-api repository.
The audit table’s uneditable property (NFR-11) rests on three independent layers: privileges (the application role cannot update or delete), triggers (even a privileged session is rejected) and process (no administrative interface offers editing). 13. Security Design
13.1 Authentication Design
Passwords: Argon2id with parameters at or above the current OWASP minimum recommendation, tuned on the production host; a pepper stored as an environment secret is optional.
Tokens: access token about 15 minutes, signed with an asymmetric key so that other services can verify without the secret; refresh token random, stored hashed, rotated on every use, family revoked on reuse (NFR-04, FR-CUS-32).
Riders: phone and OTP at sign-up (FR-DEL-1.1, NFR-09), then token-based sessions bound to a device identifier; new device requires OTP again; biometric confirmation for money actions (NFR-10).
Administrators: password plus TOTP; recovery codes stored hashed; sessions of at most a few hours; step-up authentication (fresh TOTP within five minutes) for ban, refund, wallet adjustment and settings changes (NFR-01).
Brute-force control: per account and per IP counters with exponential lockout; CAPTCHA only after repeated failures, using a free challenge service.
13.2 Authorisation Design
Authorisation is deny-by-default: each route declares the roles allowed and the ownership rule; a missing declaration fails the build.
Resource
 | Rule
 | Cart, address, order, payment, favourites
 | The record’s customer id equals the caller (NFR-04)
 | Restaurant, menu, orders of a restaurant
 | Caller is the owner, or staff of that restaurant with a role permitting the action
 | Delivery and offers
 | Caller is the assigned rider (or the offered rider for an offer)
 | Rider wallet
 | Caller is the wallet owner; admin finance role for adjustments
 | Documents
 | Verifier role; every access logged
 | Settings and audit

 | 13.3 Transport, Headers and Origins
TLS terminates at Cloudflare and at the backend host; the backend refuses plain HTTP and the rider app rejects invalid certificates (NFR-03).
HSTS, a strict Content-Security-Policy, X-Content-Type-Options, Referrer-Policy and frame-ancestors none are set on all web apps; the admin app has the strictest policy and its own origin.
Cookies are httpOnly, secure and same-site; CSRF tokens protect cookie-authenticated mutations.
13.4 Data Protection
Encryption at rest is provided by the database and object storage providers; the team must confirm this in each provider’s documentation and record it in the compliance file (NFR-03).
KYC documents and ID photos receive an additional application-level encryption layer using per-object data keys wrapped by a master key held as a secret, so that a bucket leak alone does not expose them.
Secrets live in the hosting provider’s secret store and in GitHub encrypted secrets, never in the repository; each environment has separate keys; rotation is documented and rehearsed.
Logs never contain tokens, passwords, OTPs, full phone numbers or addresses; a redaction filter enforces this (NFR-13).

 | 14. Regulatory and Data-Protection Compliance Design
Non-negotiable NN-1 requires ART/ANTIC certification and NECAP interconnection before the first live transaction. This chapter turns that obligation, and the data-protection obligations that apply to a platform handling addresses, phone numbers, identity documents and location, into design elements. It is an engineering view, not legal advice: every item marked to confirm must be checked with a lawyer or the competent authority before launch.
14.1 Live-Mode Regulatory Gate
The platform setting regulatory.live_mode defaults to false in production. While it is false, checkout, payouts and wallet top-ups run only against the payment sandbox and orders are marked as test orders. Live mode can be enabled only by the super administrator when all three compliance flags are set, and the change is audited.
The gate is enforced in the payments module and in the dispatch module (not only in the interface), so a misconfigured client cannot bypass it (FR-SYS-08).
14.2 NECAP and ART Reporting Design
The RegulatorReportPort receives a ReportableEvent after each definite payment outcome, payout, refund and SMS sent.
Events are written to a regulator_outbox table in the same transaction as the business change, then delivered by a worker with retry and backoff, so a regulator outage never blocks an order but never loses a report either.
The proposed payload fields are: event type, platform transaction reference, provider reference, amount, currency, channel, timestamp, and a pseudonymous party identifier; the final format is dictated by the regulator.
14.3 Data Subject Rights and Consent
Consent and notices: the privacy notice and terms are versioned documents (FR-CUS-33); acceptance of a version, with time and app version, is stored per user. Riders accept data-processing consent before activation (FR-DEL-1.4); merchants accept terms at registration.
Deletion: deleting an account anonymises personal columns (name, email, phone, addresses) and keeps financial records under a pseudonymous key for the legal accounting period.
Breach procedure: a written procedure defines detection, triage, containment, notification of the authority and affected users within the period set by law (until confirmed, assume 72 hours), and a post-incident review.
14.4 Cross-Border Processing
Every managed service in the free stack runs outside Cameroon. The law restricts transfers of personal data abroad and expects authorisation or an adequate level of protection, so the design limits what leaves the country and documents the rest.

15.5 Runbooks
Short runbooks, kept in docs/runbooks, are part of the operational design:

Database nearing limits: run retention jobs, check pg-boss polling, pause workers outside operating hours, consider the paid plan.
Backend down: Cloudflare maintenance page for web; riders continue offline; failover to Profile B or redeploy.

 | OTA channel rollback to the previous update; feature flags disable a faulty feature without a new build (NFR-63)
 | Signing
 | Upload keys stored securely (Play App Signing recommended); keystore backups held by two team members
 | 16.5 Database Migrations in Deployment
Migrations run in CI before the new API version starts and are written to be backward compatible (expand, then migrate data, then contract in a later release) so that the old API version keeps working during the rollout.
Destructive migrations require a fresh verified backup (Chapter 11.7) and a second reviewer.
